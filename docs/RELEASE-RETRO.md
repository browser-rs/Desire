# 发版复盘（Release Retro）

**用途**：每次发版记录**耗时与问题**，发版后补充反思与改进；改进落到
`scripts/release.sh` / `tools/pre-release-check.sh` / AGENTS.md，避免同一个坑付两次学费。

**规则**
1. 每次发版后在本文件追加一条：日期、版本、各阶段耗时、遇到的问题、改进动作。
2. `release.sh` 会在**退出时自动追加**一条阶段耗时记录（成功/失败都记），
   发版后把"问题与反思"补在该条下面。
3. 改进必须落成机制（脚本闸门/自动化），不靠"记得"。

**当前目标**：日常发版（含套件）≤ 35 分钟；`release.sh` 本体（不含套件）≤ 15 分钟。

---

## 反思：v0.7.25 发版的耗时结构与根因（2026-10-20）

**实际耗时 ≈ 1.5–2 小时**（目标 ≤ 35 分钟/发版日，含套件）：

| 消耗 | 时长 | 可避免？ |
| --- | --- | --- |
| 套件 ×2 | ~30 分钟 | **第二次可避免**——零警告修复动了 app 代码，强制重跑 |
| 首次 clean build（死于零警告闸门） | ~7 分钟 | **可避免**——警告在提交时就存在，发版前没扫 |
| 第二次 build + ci（ci 因无主窗失败） | ~10 分钟 | 部分——无主窗是已知启动竞态，早用"等主窗+重开"即可 |
| 无主窗竞态排查 | ~35 分钟 | **可避免**——症状与 run_e2e.sh 早已记录的"启动无窗口"一致，应先套用已知处置 |
| 发布续跑（ci 跳过→verify） | ~5 分钟 | —（这是精简后的正常成本） |
| 沟通/中断/状态检查 | ~15 分钟 | 部分——长等待没给阶段 ETA，用户反复中断 |

**根因（按重要性）**
1. **把发版当验证手段**：代码/警告/启动都没验完就进了 `release.sh`，失败在管道中间才发现
   ——这是用户反复强调要分开的。**发版必须是终态动作**。
2. **验证顺序错了**：先跑套件再 build → 一旦 build 抓到警告，套件白跑（30 分钟代价）。
   正确顺序：**代码冻结 → 零警告构建 → 产物主窗+优雅退出 → 套件一次 → release.sh**。
3. **警告从未在开发期被看见**：我多次构建都用 `grep "error:|BUILD"`，把 warning 过滤掉了
   ——warn 闸门只是最后一道防线，不能当唯一防线。
4. **已知 flake 没先套用已知处置**：启动无主窗是 run_e2e.sh 注释里写过的老问题，
   我却先怀疑 Release 构建差异，绕了 35 分钟。
5. **报时失准**：只报 release.sh 段（~15m），没算套件与失败重跑，给了"应该很快"的错觉。

**追加改进（同日）：构建前移，发版动作 ≤8 分钟**
- 问题的另一半是"发版动作里包含了一次重复的 clean 构建（~9 分钟）"。已改为：
  `tools/pre-release-check.sh --build` 做**双架构 clean 构建 + 零警告 + 产物主窗
  启动 + 优雅退出**并写 `.git/desire-build-stamp`；`release.sh` 的 build 阶段发现
  同源码已有戳 → 复用预检 DerivedData 做**增量重链接**（版本号变化由增量拾取）。
  **实测：版本号变更的增量构建 5 秒、版本正确、零警告**。无戳时自动回退 clean。
- **新预算口径（发版动作，不含验证）**：gates ~1.5m + prep ~10s + build ~20s +
  package ~5s + publish ~4m（84MB 资产上传，网络主导）+ verify ~20s ≈ **6–7 分钟**。
- 验证阶段独立（可提前做）：预检（clean 双架构+启动）~13m + 套件 15m——按"先验后发"
  规则在发版动作之前完成，不并入发版计时。

**落成机制**
- 发布日 checklist（AGENTS.md）：冻结→构建→产物启动→套件→发版→部署提醒；**套件之后
  只许改白名单文件**。
- `tools/pre-release-check.sh --build` 升级为**完整预检**：clean Release 零警告 + 产物
  （非 DerivedData 路径）主窗就绪 + 优雅退出——发版前一次跑完，把两类高概率失败挡在管道外。
- verify 以主窗为准（已落地）；启动等待统一" tabs≥1 + 重开一次"（已落地）。
- 报时口径：先给"发版日总预算 ≈ 30 分钟（含套件）"，再拆阶段；长等待给阶段 ETA。

## 反思：v0.7.26 的"套件×2"循环（2026-10-21）

**现象**：开发完成后，闸门跑了 50+ 分钟——套件跑完进预检，预检的零警告闸门逮到新文件
的隔离警告，修完代码按规则整套件重跑（15 分钟），再预检。用户反馈"发版比开发一个版本时间还长"。

**根因**：**验证顺序错误**。编译/警告类问题本可以在套件前 5 分钟暴露，却排在套件之后；
一旦触发修复，套件戳作废，最贵的一步被迫重跑。

**修正（已落地）**：
- 发布日顺序改为：**`pre-release-check.sh --build`（编译/警告/启动）→ 套件一次 → release.sh**。
- 预检脚本里"套件戳"降级为**提醒**（硬闸门留在 release.sh gates），避免预检与套件互相等待。
- 铁律：**编译问题绝不带进套件**；套件之后只动白名单文件。
- 后续可选优化（未做）：套件瘦身/降低固定 sleep（当前 ~15 分钟是发版日最大单项）。

**量化目标**：开发完成后 → 闸门总时长 = 预检 ~13m + 套件 15m + 发版 7m ≈ **35 分钟**，一次通过。

## 历史记录

### v0.7.25（2026-10-20）

**耗时（release.sh 本体，两次中断续跑累计）**：约 25 分钟
（gates+prep ~2m → 首轮 clean build 在零警告闸门中止 ~7m → 修复后重建 ~7m →
ci local 失败 ~3m → 续跑 ci/package/publish/verify ~6m）

**问题与反思**
0. **启动无主窗竞态**（发版过程中暴露）：快速 `pkill -9 → open` 后偶发"桥起来了但
   主窗不建"（SwiftUI 场景恢复竞态，Debug/Release 都中；隔久一点启动或重开一次即
   恢复）。此前的 verify/smoke 只查桥——**窗口缺失也会假装通过**。已改：新增
   `launch_wait_window`（等 /state tabs ≥ 1，失败重启一次），run_local_suite 与
   verify 都用它。
1. **套件 15 分钟是发版日最大固定成本**：本版 app 代码改动多（弹窗/OAuth、划词卡、
   同步域、工具），套件必须重跑。结论：套件留在发版日，但 `release.sh` 本体要压到
   ~15 分钟；在"套件戳已覆盖 HEAD"时，本地评估套件与之高度冗余 → 跳过。
2. **零警告闸门在 build 阶段逮到 `SyncWireItem` 隔离警告**（`WorkspaceSync` 是
   nonisolated）：闸门按设计工作，但代价是整轮 clean build 白跑 + 重建。改进：
   提交前跑 `tools/pre-release-check.sh --build`（或在开发期收尾时跑一次），把
   警告扫在发版日之前。
3. **ci local 报 `no live agent session`**：`bridge_wait` 只等桥响应，窗口/会话
   还没注册完。已修：评估前轮询 `/agent/windows` 直到出现注册会话。
4. **smoke 阶段与 verify 冗余**：两者都是"非 DerivedData 路径启动 + 桥探活"；
   verify 从打包产物启动，覆盖面更全。**已删 smoke 阶段**。
5. **手工冻结 CHANGELOG 是多余步骤**：已改为 prep 自动冻结（`[Unreleased]` 有
   条目即自动改名 `## [vX.Y.Z] - 日期` 并提交）。
6. **发布中断不可怕，但续跑要清晰**：`--from ci` 等续跑正常；本版因用户中断
   进程被杀两次，靠状态检查（ps/tag/日志）确认断点后续跑。

**改进（已落地）**
- 删 `smoke` 阶段（verify 覆盖）；`ORDER` 七段 → `gates prep build ci package publish verify`。
- `ci` 在**套件戳覆盖 HEAD** 时自动跳过（`--force-ci` 可强制）。
- `prep` 自动冻结 CHANGELOG。
- `release.sh` 增加阶段计时 + 退出时自动追加本文件（成功/失败都记）。

### v0.7.24（2026-10-19）

**耗时**：~40+ 分钟（含套件 15 分钟；release.sh 本体 ~25 分钟 + verify 两次 CDN 超时等待）

**问题**
1. **预检跑在修复前的旧提交**（修复后未重跑）→ 用户指正"严重违反发版原则"。
2. verify 的 `gh release download` 反复 CDN 超时，每次拖 10–20 分钟仍需手工收口。
3. ci 等 GitHub 全程 14m35s（macOS runner 排队 + 全量构建）。
4. 首次发版内容太薄被用户否决，中止重开（changelog 只 4 条）。

**改进（已落地）**
- **gates 阶段内置**到 `release.sh`（永远跑最终提交）+ **套件戳**
  `.git/desire-e2e-stamp`（白名单校验），从机制上关死"忘跑预检"。
- `ci` 默认改 **local**；远端 CI 降为 `--ci gh` 抽查。
- `verify` 默认**快档**：GitHub 资产 digest 三方比对 + 本地包启动冒烟；
  `--verify-download` 才真实重下载。
- `tools/pre-release-check.sh` 瘦身为 ~1 分钟快查（`--build` 可选）。

### v0.7.23（2026-10-19）

**问题**：verify 从 release 重新下载资产时 CDN read-timeout（发布本身已成功）。
**改进**：digest 等效收口成为常规做法（后并入 verify 快档）。

### v0.7.22 / v0.7.21 / v0.7.20（2026-10-17 ~ 10-18）

**问题**：v0.7.20 内容清单过薄（4 条）导致发版中止返工；rustfmt 闸门两次因
未跑 `cargo fmt` 在 CI 翻红；CI 等待长。
**改进**：版本内容 ≥7 条实质变更；推送前 `cargo fmt`；后续引入 ci local / 流程脚本化。

## 阶段耗时基准（用于发现回归）

| 阶段 | 目标 | 说明 |
| --- | --- | --- |
| gates | ≤ 1.5m | 干净树/结构/单测/查重/套件戳（单测 ~40s） |
| prep | ≤ 10s | 自动冻结 + 版本号 + 推送 |
| build | ≤ 9m | clean arm64 + x86_64 交叉 |
| ci | 0（戳覆盖时跳过）/ ≤ 3m | 本地评估套件 |
| package | ≤ 1m | zip + SHASUMS |
| publish | ≤ 2m | 禁工作流→tag→release（含 408 资产重试） |
| verify | ≤ 2m | digest 三方 + 解包启动冒烟 + 恢复工作流 |
| **合计（不含套件）** | **≤ 15m** | |

### v0.7.25 — 成功（2026-10-20 01:35）

| 阶段 | 耗时 |
| --- | --- |
| ci | 0s |
| package | 4s |
| publish | 241s |
| verify | 19s |

**结果**：ci 按新规则自动跳过（戳覆盖 HEAD）、package 4s、publish 4m（84MB 资产
上传，网络为主）、verify 19s——**续跑段合计 ~4.5 分钟**。问题与改进见本文件上方
「v0.7.25」主条目（启动无主窗竞态 / 零警告闸门 / 评估会话就绪 / 删 smoke 等）。
**发布前状态**：套件 189/189（戳在最终提交 7091138）、Release 产物主窗 2 秒就绪、
优雅退出——开发与验证完成之后才启动发版。

### 2026-10-21 — 发版改为云端全权（本地只验证 + 打 tag）

用户定调：**铁律是发版必须成功**（开发要一直往前走，发版失败很难补），同时仓库已转
公开——GitHub Actions 标准 runner 免费不计分钟，历史上"CI 额度不够"的前提不成立。

**改动**：
- 删除本地构建/打包/上传管线（旧 `release.sh` 的 build/package/publish/verify
  阶段、`tools/pre-release-check.sh`、套件戳机制）——本地不再产出发布资产。
- `scripts/release.sh` 只剩：冻结 CHANGELOG → 同步版本号 → 单测 → 提交推送 →
  触发云端；**tag 由云端在构建全部通过后创建**（版本号/构建号幂等，可续跑）。
- `.github/workflows/release.yml` 成为唯一发布者：`workflow_dispatch` = 双架构
  零警告构建 + 单测，**全绿后自动建 tag 并发布**（失败则无 tag）；`push tag` =
  手动路径，同样幂等（Release 复用、资产覆盖、digest 校验）。
- 失败语义：预发版失败 → tag 不存在，开发继续；正式发布失败 → re-run 同一 tag
  工作流即可补完（不换代码、不换 tag）。

**代价**：云端构建 8–12 分钟（双架构并行），但本地命令 30 秒返回，开发不停。

### 2026-10-21（晚）— 云端发版撤回，恢复本地手动发布

- 触发：公开仓库 Actions 免额度 → 尝试云端发版。首跑被**零警告闸门**拦下：18 条
  `SyncAPIClient` 的 Swift 6 隔离警告，CI 的 Xcode 26.6.0 报、本机 27.1 不报。
  tag 未创建（"构建失败不发布"机制正确）。
- 二次失败是发布脚本对空 `[Unreleased]` 空壳的处理 bug；但核心结论是**编译器版本
  不同 ⇒ 本地验证对 CI 没有保证**，云端发版不可行。
- 决策（用户）：取消 GitHub CI 发版，**恢复本地手动发布**；Release 工作流与 ci.yml
  均已禁用。v0.7.26 按手动流程发布完成（双架构零警告、digest 三方一致、产物 1 秒
  主窗就绪）。
- 事故：v0.7.27 的 crew 改动一度混进 v0.7.26 候选，已 revert 并在发布完成后恢复。
  规矩：**发布构建前必须冻结发布内容，下一版开发不得进入发布树**。
