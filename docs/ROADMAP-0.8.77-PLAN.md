# v0.8.77 规划稿（2026-11-25）—— 准确的批量下载：浏览器取地址、引擎下分片、站点技能定正片

> **背景**：v0.8.76 发版当晚的真实使用里，内置批量下载被智能体弃用——它自己写了
> 脚本下载，并存下一条"绝不要用 `downloadVideoList`"的站点技能。本版只做一件事：
> 让内置的批量下载重新成为这条路线上**最准、最快、最省心**的选择，并且让智能体与
> 浏览器在这件事上真正协作。
>
> **用户定调（四条，长期有效）**：
> 1. 目标是**排除杂项后的准确正片集合（可能一个，也可能多个）**——不是"一页一片"。
>    有的站点详情页有多个正片；有的只有一个但混着广告、预览、缩略图。
> 2. **每个站点的技能专属**，按站点绑定，不能混用——每个站点情况都不一样。
> 3. **站点技能要在后续下载任务里不停打磨**，不是一成不变的。
> 4. **Agent + Browser 是一体的**：需要浏览器能力（Cookie、过 Cloudflare、现取签名
>    地址）就用浏览器；脚本/引擎负责吞吐；不要让模型用一个脚本硬扛所有问题。

## 规划前核实（代码 + 当晚会话轨迹；站点信息不入库）

| 现象 | 核实结果 |
|------|---------|
| 24 个页面排出 33 个任务、同一部出现 4 次、文件全是 7KB 碎片 | 嗅探脚本把 `.ts` 分片判成 `video`；规划层 `distinctMediaFamilies` 按"主机 + 文件名主干"聚类，**每个分片主干不同 → 各自成簇 → 各算一个视频**。`downloadableResources` 只滤 blob / DASH / IAB 广告尺寸，**没有分片过滤** |
| 解析后"其余全部"都成了下载项 | `BatchMediaExportStore`：`pickBestResource` 选一条主项，其余 `distinctMediaFamilies` 一律追加为"兄弟项"（上限 4）——**没有"杂项"这个概念** |
| 多视频的详情页会漏 | `HeadlessMediaResolver.awaitMedia` 第 ⑤ 步：`pickBestResource(captured) != nil` **即返回**——第一个可下载资源一出现就收工，需要点击/滚动才加载的其余视频不会被看到 |
| 一部 2 小时的片要 2 小时以上 | 两条引擎都**串行**抓分片：`FFmpegExporter` 单进程 `-i playlist`；内置 `MediaExporter.download` 是 `for segment in segments`。当晚实测单连接约 160KB/s |
| 默认配置下长片必然失败 | 导出默认超时 30 分钟；批量默认并发 2。按串行速度，1.2GB 的片在超时前只能下到约四分之一 |
| 智能体的脚本快 14 倍 | 它并发抓加密分片到本地 + 本地播放列表交给 ffmpeg 解密合成：24 线程 563 秒下完 1239MB（≈2.2MB/s）。实测 32 连接约 6 分钟/部，64 连接开始大量 SSL 失败 |
| 智能体脚本反而把地址时效做坏了 | 它一次性抓了 24 个签名地址（约 1 小时过期），到第 2 部就失效。内置 list 批量本来就是"按下载槽节奏、开下那一刻才在隐藏浏览器里解析"——**设计是对的**，输在上面几条 |
| 它存了一条"绝不要用批量下载"的技能 | 不处理的话，这条路线会被永久绕开 |

## 设计：三者各管一段

- **浏览器**负责身份与时效：Cookie / Cloudflare / 页面知识，签名地址在**开下那一刻**才取。
- **引擎**负责吞吐与可靠性：分片并发、断点续传、地址中途过期后重新解析、限流自适应。
- **站点规则（DPP 适配器）**负责"什么才是正片"：按域名绑定的**可执行规则**，每次任务
  都可能回写打磨；技能只留说明。
- 没有适配器的页面走**通用规则 + 证据**；拿不准的不猜，交给智能体看页面确认一次，
  确认结果写回该站适配器。

## 批 1：正片识别（正确性）

**纯逻辑（`BatchMediaPlan`，进 harness）**
- **分片归并**（结构性判断，不是按个数一刀切）：`.ts / .m4s / .aac / .cmfv…` 满足
  "同页有播放列表且目录有亲缘"，或"同目录有 ≥3 个连号命名的同扩展名资源"时判为分片，
  归并进所属播放列表；只有当 `.ts` 是页面上**唯一**的媒体时才当视频。
- **杂项判定并给出理由**：广告（IAB 尺寸 + 路径/域名特征，按路径段整词匹配，
  `download` 这类含 `ad` 的词不误伤）、预览/缩略图（`_preview`、`thumb`、`poster`）、
  分片、过短（见下）。
- **时长证据**：`playlistDuration`（解析 `#EXTINF` 求和）；短于阈值（默认 90 秒）判为
  杂项，**除非它是页面唯一候选**（短正片也成立）。直链文件的时长未知 → 不据此判。
- **输出候选表**：每个候选带证据（类型、时长、大小、来源播放器、URL 特征、判定理由），
  另有被拒清单（地址 + 理由）。多视频页每个正片一个任务，取消"最多 4 个兄弟项"的上限。

**解析器（`HeadlessMediaResolver`）**
- 不再"见到第一个资源就收工"：首个候选出现后进入**稳定窗**（一段时间没有新候选就收），
  期间分步滚动触发懒加载播放器、逐个点播放、收集页面上所有 `<video>`（尺寸、时长、
  位置）；页面只有一个播放器且已在播放时提前结束，单视频页不明显变慢。
- 解析结果带上候选表与证据，供引擎与智能体使用。

## 批 5 进展（2026-11-26）：前台实测与修复

`tests/batch-content-e2e.py` 首轮 34/44，暴露四处真问题，都已修并回归（harness 3855）：

| 现象 | 根因 | 修法 |
|------|------|------|
| 站点规则对声明过的详情页不生效（带规则的页面全走了通用识别） | **既有 bug**：系统的 `URL.path` 不带路径末尾的 `/`（`…/aaa-001/` 读出来是 `…/aaa-001`），对前缀 `/videos/aaa-001/` 做 `hasPrefix` 永远不成立。按目录写前缀的适配器（页面协议与下载规则都受影响）从来匹配不上"路径恰好等于前缀"的地址 | `DPPAdapter.path(_:hasPrefix:)`：相等单独判；目录形式的前缀仍只在段边界生效（不放宽） |
| 多视频页同一部出现相对、绝对两份，相对的下载报"不支持的URL" | 嗅探脚本的 `src-attr` 钩子上报原始赋值串（懒加载播放器写 `video.src = '/hls/…'`），XHR / fetch 的回退分支同理 | `media-sniffer.js` 上报前按文档基准地址补全；`contentCandidates(baseURL:)` 兜底解析 + 去重 |
| 过期停机时把在途分片一起取消，续传要重抓 | 达到阈值后 `cancelAll()` | 只停止补位，在途的抓完即复用 |
| 批次日志看不出哪一页按规则解的；12 秒的片显示"0 分钟" | 规则命中且无排除时不写日志；时长只按分钟取整 | 规则产出必写一行；不足一分钟写秒 |

最终：**45/45**（`batch-content-e2e.py`：listPageVideos 三种页面形态 + 五页批量 7 条正片
+ 规则命中 / 落空 / 过期续传 + 有效期 50→30 与修订备份 + 分片不重抓 + 技能同步与撤回）、
**10/10**（`parallel-hls-e2e.py`）、`resolveVideos` 直接调用实测（多视频页 3 条、地址全为
绝对）。测试夹具随之修正两处：多视频页的流改成 100 秒（12 秒的流会被"短于 90 秒且页面上
还有别的候选"这条规则剔除——规则本身符合预期）；`/expire/` 改成确定性语义（出现过 403
之后重取播放列表才恢复——解析阶段的时长探测也会取一次播放列表，不能再数"第一次请求"）。

**已知取舍**：页面上同时有短正片（不足 90 秒）和别的候选时，短的那个会被当成广告 / 预览
剔除。**余项**：190 全量（需机器空闲）、What's New、真实站点效果（需本人使用）。

## 批 2：站点专属规则——DPP 适配器为主、技能为辅（活的）

**载体选择（2026-11-25 用户提议"用自定义 DPP"，核实后采纳）**。DPP 适配器本来就是
为"按站点适配"造的：按主机（精确或 `.后缀` 通配）+ 路径前缀绑定、纯 JSON 声明式、
可从文件/URL 安装、有 DPP Studio 编写界面、有健康记录（成功/失败计数、最近错误）、
能启用停用、有官方运营包——"只对本站生效、不能混用"是它的固有语义。

| 现状 | 能做 | 做不了 |
|------|------|--------|
| DPP 适配器 | 列表页视图（条目选择器 + 字段 + 翻页 + 噪音区）、页面类型、正文分区、声明式动作 | ① 从内联脚本里提取流地址（字段表达式只有选择器/属性/文本，没有"对脚本文本求正则"）；② 下载参数（连接数、地址有效期、每页正片数）；③ **隐藏解析器不读适配器**——只有普通标签页用 |
| 技能 | 给模型看的做法说明、触发直通、使用统计与纠正补丁 | 引擎不能执行；今晚模型就是照着自己的说明书去写了脚本 |

**分工**
- **适配器 = 站点规则的唯一真相**（引擎与智能体都执行同一份）：新增 `download` 规则段
  ——详情页提取规则（对页面脚本/HTML 文本的正则，或选择器+属性）、列表页用哪个视图、
  每页正片数（one / many）、排除特征、每路连接数、地址有效期。列表页继续用既有视图 +
  `pageExtract(view, all: true)`（翻页一次取全）。
- **技能 = 说明，不再写提取细节**：这个站点有适配器、直接用批量下载、已知的坑。
  适配器保存/更新时由引擎同步这段技能，避免两处各写一份互相漂移。
- **引擎接线**：隐藏解析器加载页面后先查该主机的适配器，有 `download` 规则就按规则
  确定性提取；规则失效（提取不到）才退回通用采集，并标记该规则待重学。解析器里只跑
  提取表达式，不注入整套协议脚本（Cloudflare 挑战页对全局补丁敏感，是既有约束）。
- 站点自己将来声明了 DPP（页面原生声明优先于适配器）时，下载规则跟随站点声明——
  与协议"适配器只补空白"的原则一致。

**每次任务回写打磨**（用户第四条；适配器的健康记录已经在，补上"自动调整"）
- 地址中途过期（403）→ 缩短地址有效期；
- 被限流 / 大量连接错误 → 降低每路连接数；
- 提取不到 → 记失败、标记待重学，交给智能体重新看页面后更新适配器；
- 用户在任务中的纠正（"这是广告""漏了一个"）→ 改排除特征 / 每页正片数 / 提取规则
  （沿用 v0.8.76 的纠正补丁机制：提出 → 确认 → 落盘并备份旧版）。
- 参数类调整有上下限并留修订记录；设置页的适配器健康区能看到这个站点规则的演变。

## 批 3：速度（分片并发）

- **有 ffmpeg**（已有首选路径）：并发抓**加密分片**到临时目录 → 写本地播放列表
  （密钥指向本地文件）→ ffmpeg 解密合成（当晚智能体验证可行的路径）。
- **没有 ffmpeg**：内置循环做有界并发，分片落盘、按序追加（不把整片读进内存）。
- **总连接预算**：每路默认 8、批内合计上限 32；遇到 429 / 5xx / 连接错误自动减半。
- **中途过期**：剩余分片 403 → 触发重新解析页面 → 只补缺失分片（分片级断点续传）。
- 进度按分片上报；合成阶段继续上报。

## 批 4：工具与提示词（让智能体用得上）

- `resolveVideos(pageURLs)`：浏览器现取，返回候选表 + 证据 + 预计过期时间。
- `downloadVideoList`：新增"几部并发、每路几连接"参数；说明重写为
  "任务只存详情页地址；签名地址开下时才取；命中站点规则时自动按规则；不要自己预抓地址或写脚本"。
- 拿不准时（多个候选且证据分不出主次）→ 返回待确认清单，智能体确认后写回该站适配器。
- 提示词：需要站点 Cookie / 过 Cloudflare 的请求走页面内 fetch，不用命令行直连。

## 验收

| 指标 | 目标 |
|------|------|
| 单视频 + 杂项页 | 只下正片；碎片、预览、广告 0 个 |
| 多视频页 | 每个正片各一个任务；不漏、不重 |
| 站点规则（适配器） | 只对绑定的主机/路径生效 |
| 限速 HLS 上长片耗时 | 并发路径比串行快 ≥ 5 倍，且在默认超时内完成 |
| 中途过期 | 自动重新解析并续传，无需人工 |
| 当晚那类页面（24 页列表） | 任务数 = 正片数；不再出现碎片文件 |

浏览器相关的验收已在前台封闭实例上跑完（见「批 5 进展」）；真实站点上的效果待本人使用。

## 不做

- 通用"一页一片"规则；跨站点共享的下载规则；在技能正文里再写一份提取细节。
- 让模型每轮现写下载脚本（提供工具与规则，脚本只在工具确实覆盖不了时才用）。
- 绕过 Cloudflare 或验证码（保持"不绕过，等待"）。

## 风险

- **稳定窗拖慢单视频页**：只有一个播放器且已在播放时提前收尾。
- **并发触发限流**：总连接预算 + 自动减半 + 站点技能记忆该站的合适并发。
- **规则把正片排除掉**：排除只在有其它候选时生效；被拒清单可见、可撤销。
- **自动打磨改坏规则**：参数类调整有上下限；规则类修改走确认。
